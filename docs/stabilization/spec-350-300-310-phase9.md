# Stabilization phase 9: OMI-SPEC-350 → OMI-SPEC-300 → OMI-SPEC-310

**Normative baselines:** OMI-SPEC-350@0.1.0 (Capability and Conformance Model), OMI-SPEC-300@0.1.0 (Plugin Architecture), and OMI-SPEC-310@0.1.0 (Platform API). All three are **Draft**, not certified interoperability protocols. In particular, 300/310 are conceptual Drafts without a complete normative test/manifest schema.

This change is implementation hardening for Studio's **narrow** already-deployed extension registry, not an OMI 1.0 conformance claim and not a general plug-in runtime or general-purpose object API.

## SPEC-350: evidence and claims

- **REQ-CON-003–005, 014–018, 021–030, 032–035:** A Studio self-assessment must be explicitly marked experimental, scoped to exact implementation/platform/dependencies, tied to a concrete suite digest and every expected requirement and test fixture. `isAssessmentCurrent` now rejects incomplete, reordered, mutated or forged case/coverage records, overclaimed independent verification, an unapproved suite masquerading as approved, and unsupported waivers **even if the unkeyed report digest is recomputed**.
- Reports remain **self-assessments**, with `verification: not-independent`, `complete: false` and `outcome: indeterminate`; successful synthetic fixtures do not establish compliance.
- The Studio capability disclosure now explicitly includes separate OMI-SPEC-300 and OMI-SPEC-310 Draft scope and prerequisites. Unknown or absent support must not be promoted to supported.
- Critical distinction: SHA-256 alone is **not** proof of authenticity or independent verification. A malicious issuer can create a fresh internally consistent report; a formal verifier requires independently checked signatures, fixtures, build identity and profile approval.

## SPEC-300: restricted plugin-manifest boundary

- The existing Studio extension registry remains declarative: it stores registration metadata only and **never executes untrusted plugin scripts** or grants document access.
- `server/src/integrations/extensionManifestSchema.ts` now centrally declares API v1 and an explicit permission allowlist. Unknown or out-of-version fields and non-semver implementation versions fail closed.
- Duplicate permission/mode/capability declarations, mixed unauthenticated/authenticated modes, non-HTTPS, URL credentials and local/IP-literal hosts are rejected.
- Manifest registration is still bound to authenticated Studio user scope. There is **no** automatic dependency graph, lifecycle execution, extension sandbox, OMI event stream or transitive authorization. Real execution needs separate permission-aware adapters.

## SPEC-310: version-bound API discovery

- New **authenticated** `GET /api/integrations/extensions/capabilities` declares the currently accepted API version, permission vocabulary, registry scope and explicitly false code-execution, authorization and publishing flags.
- The TypeScript client can discover and reject incompatible manifests/API versions rather than assuming a remote server's implementation.
- No new general `/objects/{id}` or document CRUD implementation is implied. The API remains scoped to the existing user-specific extension registry, not a server-wide certification.
- Registration and capability discovery do not grant access to manuscripts, review records, secrets, authoring actions or publishing.

## Regression and release evidence

- Unit tests: altered claim digests and recomputed fake claims, partial evidence/extra or missing result rows, wrong suite approval and claimed independent verification.
- Server schema tests: allowed manifest, unknown permissions, unsupported API version, mixed `none` + OAuth, unsafe URLs and unknown manifest fields.
- These tests are mandatory in Studio CI, **not** a replacement for independent OMI-SPEC conformance fixtures, privacy penetration tests, interop tests or user acceptance.

## Nine-stage release gate

Phase 9 completes the planned **development package** only, not the nine-stage certification/release process. All open Draft PRs (especially phase 8 #794) must be independently reviewed, merged sequentially and shown green on final main SHA. Then a cross-phase final assessment must include long DOCX/ODT/.omi files, editing freedom, review confidentiality, asset integrity, JATS/HTML/PDF, live collaboration/API permissions, federated server behavior, mobile and desktop workflows, and outstanding blocker decisions. Draft specifications remain Draft unless their own governance process explicitly promotes them.

**Do not bump Studio, Android, iOS or website release versions until a single final acceptance authorizes it.**
