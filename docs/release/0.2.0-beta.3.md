# Open Manuscript Studio 0.2.0-beta.3

Status: final stabilization beta
Date: 2026-09-20
Next planned milestone: v1.0.0-rc.1

## Release purpose

0.2.0-beta.3 is the final planned beta on the Route A path to Open Manuscript
Studio 1.0. It freezes the current feature boundary and packages the
stabilization work completed after 0.2.0-beta.2.

The release is intended to collect real-device and real-manuscript evidence.
New editing features should not be added after this beta unless they are needed
to remove a release blocker.

## Included stabilization

The release includes:

- central OMI, institutional OIDC and local Studio sign-in paths with explicit
  identity-linking boundaries;
- the canonical OMI-SPEC-320@0.2.0 standalone manuscript boundary;
- the complete all-features reference manuscript and browser lifecycle gate;
- explicit JATS release blocking when the source manuscript contains
  fallback-only semantics;
- OJS 3.5.0-4 and 3.5.0-5 Stable acceptance evidence;
- OMP 3.5.x retained as Preview;
- security, accessibility, recovery, update and installer hardening gates;
- Windows MSI install/uninstall and Linux DEB install/uninstall CI round trips;
- Android package/signature verification and recorded physical-device
  install → update → uninstall acceptance;
- the long-manuscript header layout correction that removes the document title
  from the global application header.

## Mandatory automated evidence

Before merge/tag/publication, require green results for:

- OMI Studio CI/CD;
- 1.0 Readiness;
- CodeQL;
- PKP integration environment, including both OJS Stable targets;
- Tauri Builds and Releases, including Windows/Linux installer round trips and
  Android package verification;
- iOS simulator smoke build as Experimental evidence.

A failing Stable-platform or security/data-integrity gate blocks the beta.

## Release procedure

1. Merge the beta.3 preparation PR only after all pull-request gates are green.
2. Let the protected-main Tauri workflow build the immutable desktop/native
   release artifacts for tag `v0.2.0-beta.3`.
3. Run **Android Release** as a new workflow run; verify the derived
   versionCode is >1050 before any Play upload.
4. Publish the Android AAB to the selected testing track and retain the signed
   direct APK artifact.
5. Confirm the hosted web deployment reports 0.2.0-beta.3.
6. Link the successful release/evidence runs from the Route A tracker (#390).
7. Mark “Publish the final stabilization beta” complete only after the release
   artifacts and hosted deployment are actually available.

## Transition to RC1

After beta.3 is published, changes on the path to `v1.0.0-rc.1` are limited
to release-blocking fixes, reproducible regressions, translations and
documentation. The first RC starts the formal 2–4 week evidence period defined
by the Route A plan.
