# Tauri main-WebView CSP and EuroOffice isolation

Status: **staged security hardening / beta acceptance required** (issue #770). As the hosted Studio currently serves a limited tester cohort, the native changes may be accepted through a controlled beta deployment **after CI and rollback verification**, without provisioning a separate test server. The CSP is active in the proposed Tauri source, but completion of #770 still requires verified Windows and Android behavior. Do not mark the issue resolved based on static tests alone.

## Threat and trust boundaries

Previously, `src/components/PlainDocumentWorkspace.tsx` loaded `DocsAPI` using a `<script>` element in the **privileged main Tauri WebView**. That script URL comes from the configured EuroOffice server and may vary across institutional installations. A global `script-src https:` exception would allow arbitrary remote scripts to run in Studio's native-privileged context and would not be an acceptable CSP remediation.

The staged architecture has these boundaries:

1. **Main Tauri WebView:** `app.security.csp` allows scripts only from `'self'` (plus `'wasm-unsafe-eval'` for Wasm instantiation), with script attributes, object embedding and `unsafe-eval` disallowed. Bundled script nonces/hashes are still generated by Tauri.
2. **Native capabilities:** `src-tauri/capabilities/default.json` grants permissions to **webview `main`** rather than all WebViews created in the main OS window. No `remote.urls` capability is configured. Browser windows for bibliography providers do not gain Studio's native filesystem/dialog grants.
3. **Office host:** the selected Studio API serves `GET /api/v1/eurooffice/embed-host?channel=<random>` as an HTML document with an independent, origin-specific CSP. The endpoint has **no session token, document content or editor configuration**. It loads only the DocsAPI JavaScript from the server-configured `EUROOFFICE_URL` origin.
4. **Editor session:** the privileged main window obtains an owner-authorized launch through the existing API using the selected server and native bearer session. The launch (which contains a short-lived editor token) is sent by `postMessage` only to the exact expected API-origin iframe, after verification of both `event.source` and a randomly generated channel. The host accepts messages only from the configured frontend or known native Tauri origins. Native Office source code is not injected into the main document.
5. **Office renderer:** the sandboxed iframe has no top-navigation permission and its separate CSP limits scripts and child frames to the configured Office origin. The only documented broad remote allowances in the **main** CSP are `connect-src https:/wss:` (necessary for user-selected federated servers) and `frame-src https:` (necessary for a separately origin-verified institutional editor host). These are **not** exceptions to the main `script-src`.

The normal browser Studio continues its existing integrated EuroOffice API loading path; the installed Tauri client takes the isolated-frame path. No OMI manuscript model, DOCX storage format or permission model is changed.

## Build and deployment sequence

1. Deploy the **Studio API** with the new `/api/v1/eurooffice/embed-host` route and verify it returns HTTP 200, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and a CSP with the installed EuroOffice script **origin only**.
2. Deploy the matching Studio web source. Browser EuroOffice behavior should remain unchanged. Keep the API server deployed before shipping any native build that expects its embed-host endpoint.
3. Build Windows and Android native packages from the PR commit; inspect the effective Tauri CSP in the application WebView console and verify script injection, malicious onerror handlers and `javascript:` payloads do not execute in Studio.
4. Open a real DOCX in EuroOffice using a centrally hosted and an institutional Studio server. Verify editing, nested iframe bounds on Android, Save/force-save/final-close callbacks, reopening and crash snapshot recovery.
5. Test ORCID/OIDC return, separate bibliography windows, native open/save scopes, editor rendering, KaTeX/MathML/SVG, PDF/IDML export and cloud provider APIs. Verify iframe origin is different from native main origin and that remote Office content cannot invoke native IPC or filesystem APIs.
6. Verify iOS simulator build and smoke test. For the tester-only rollout, complete the CI rollback test and confirm the Plesk snapshot before merging. After deployment, perform physical Android and Windows acceptance and revert promptly on failures; keep #770 open until both are verified.

## Tester-only deployment and executable rollback

The production deployment workflow now takes a **pre-change local snapshot** on the existing Plesk VPS, under `$HOME/.omi-studio-rollbacks/<run-id>-<commit>/`. The snapshot contains the previously served `studio/httpdocs`, compiled `server/dist`, live `server/node_modules`, and prior Git commit ID. The snapshot directory is private (mode 0700). The GitHub CI runs a synthetic snapshot/restore round-trip test before any deployment can proceed.

A failed deploy automatically restores the previous checkout, exact web assets and compiled API plus runtime dependencies and restarts `omi-studio-api.service`. A manual restore is available on the server with:

```bash
bash "$HOME/.omi-studio-rollbacks/<run-id>-<commit>/rollback.sh" restore \
  "$HOME/.omi-studio-rollbacks/<run-id>-<commit>"
```

Replace `<run-id>-<commit>` with the directory name printed by the deployment log. **Do not execute a manual restore while a deployment is still running.** The script verifies the snapshot marker and exact prior commit. It does **not** restore or delete PostgreSQL, manuscript edits, external cloud packages, login data, application configuration or TLS certificates. If the new release changes either Prisma migration directory, code-only automatic rollback is disabled and the deployment fails before writing new application assets; a separately reviewed full database backup is then mandatory.

The existing Plesk deployment is sufficient for beta testing once the snapshot passes; it is not necessary to maintain a second VPS. Restore the previous signed **Windows** client if required. Android applications distributed by Google Play cannot normally be downgraded in place: a rollback of an installed Play version requires a new **signed hotfix build with a higher versionCode** built from the previous verified code. Authors should save portable OMI packages to cloud or removable storage before installing a native beta.

## Failure/rollback policy

If the hosted isolation endpoint cannot be loaded or its DocsAPI fails, the UI reports an error and **does not load the remote script in the privileged main window as a fallback**. Do not restore `csp: null` or globally enable `unsafe-eval`, `unsafe-inline` for scripts, or a wildcard remote script source to work around integration failures.

Rollback native clients using the last verified signed package if necessary; server additions are backwards-compatible with older clients. Keep issue #770 open until both security boundary tests and real EuroOffice application tests pass. The separate outbound egress and PDF worker issues (#765 and #774) are not solved by this change.
